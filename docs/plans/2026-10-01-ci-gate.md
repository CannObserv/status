# The CI gate

Issue: [#11](https://github.com/CannObserv/status/issues/11), deferred from #9 ([spec § Deferred](../specs/2026-09-30-deploy-releases-design.md)).

## Problem

`scripts/deploy.sh` puts any commit on `origin/main` live, CI green or not. CI (`lint`, `test`, `migrations`) is the only correctness signal (AGENTS.md). The deploy's own checks catch a release that does not start; they miss one that starts and is wrong, or whose migration chain fails from empty.

## Approach

Before a live deploy builds or migrates anything, ask GitHub's Actions API about the commit, and refuse unless its push run on `main` and every job in it succeeded, `lint`, `test` and `migrations` among them. The refusal names each job that did not.

- **The run that decides:** the newest `push` run of `ci.yml` on `main` whose `head_sha` is the commit. `GET /repos/CannObserv/status/actions/workflows/ci.yml/runs?head_sha=…&event=push&branch=main`, filtered again client-side, then `GET …/actions/runs/<id>/jobs`. Check runs carry no event or branch: 291604b lists each job twice (a `workflow_dispatch` run on `15-guard-alembic`, and the push run on `main`), and nothing in them tells the two apart.
- **The run and every job in it, `success` only**, with `lint`, `test` and `migrations` among them (`CI_JOBS`, the floor `tests/ci` holds `ci.yml` to). `skipped`, `cancelled` or absent fails. The run's own conclusion is not enough, since a run with a skipped job still reports `success`. `CI_JOBS` comes from the checkout running the deploy, which may be older than `ci.yml`, so a job it does not name counts all the same (CR 6).
- **Pending: wait, bounded.** Up to `STATUS_DEPLOY_CI_WAIT_SECONDS` (600), asking every 30 s. `git push origin main && scripts/deploy.sh` then works as one step; CI takes about 2 minutes.
- **No run: refused at once, unless the commit is `origin/main`'s tip.** GitHub runs CI on the newest commit of a push only (e6c8d09 and 0160e04, inside #13's push, have none), and never on `[skip ci]`. A commit behind the tip has its run already or will not get one, unless it was pushed seconds ago with another push after it; the refusal says to deploy again shortly (CR 8). The tip may have been pushed seconds ago, so it counts as pending, within the same wait.
- **`--skip-ci`** skips the question for an emergency fix or a GitHub outage. It is logged to `journalctl -t status-deploy` before anything is built. A passing gate is logged too, with the run's link. With `--dev`, refused: dev is never gated.
- **No token.** The repo is public; unauthenticated is 60 requests/hour per IP. A deploy costs 2, and at most 22 when it waits the full 600 s. No credential in the deploy path means none to scope, store or rotate, which is what deferred this in #9. A refused request (rate limit, outage) refuses the deploy with GitHub's message.
- **The whole deploy is refused, dev included.** A refused deploy changes nothing; `--dev` puts the commit on dev alone.

## Tradeoffs / alternatives

- **Any green run for the commit.** Rejected. A branch `workflow_dispatch` run tests the same tree, but with several runs the verdict would depend on which one someone ran last. A pull request run tests a merge commit, not this one. The push run on `main` exists for every pushed tip but a `[skip ci]` one.
- **Refuse while pending.** Rejected: the operator just types the deploy again two minutes later. The wait is bounded and holds the deploy lock, which is what a concurrent deploy should see anyway.
- **Wait when there is no run, whatever the commit.** Rejected: most `main` commits never get one, so a deploy of one would sit 10 minutes before refusing. A fixed grace (say 60 s) for every commit was also rejected: it guesses, where the tip rule knows.
- **`gh api`.** Rejected: `gh` here is not logged in, and refuses to call the API unauthenticated. `curl` and `jq` are already on the VM.
- **A read-only token from `/etc/status/`.** Not now. Unauthenticated covers the expected rate, and a token is a credential to provision and rotate. Revisit if the repo goes private (the API would answer 404) or the limit bites.

## Steps

1. **Tests** in `tests/deploy/test_deploy.py`, through the `curl` stub answering `api.github.com`: default green; failed (names the job, nothing built); pending past the wait; pending then green; no run for the tip, then one; duplicate runs (branch dispatch vs push on main, either way round; two push runs, the newest decides); no run behind the tip, refused at once; a run for another commit; a skipped, cancelled or absent job; GitHub refusing; an answer that is not JSON; `--skip-ci` (no question, logged before building); `--dev` never asks; `--skip-ci --dev` refused; the gate's jobs are ones `ci.yml` runs. Review added: a failed job `CI_JOBS` does not name, a cancelled run with no jobs, a run that did not conclude `success`, and other runs differing from the push run on `main` in event or branch alone.
2. **`deploy.sh`**: the gate, `--skip-ci`, `STATUS_DEPLOY_CI_WAIT_SECONDS`, and `STATUS_DEPLOY_CI_POLL_SECONDS` for the tests (CR 1).
3. **Docs**: `docs/DEPLOYMENT.md` § The CI gate, usage, variables, rollback; the spec's Deferred list; AGENTS.md.
4. **Deploy** with the gate itself, and confirm the journal line.

## Open questions / risks

- **A cancelled push run.** `ci.yml`'s concurrency group never cancels a *running* run on `main`, but a third push while one runs and one waits cancels the waiting one, and so does a dispatch on `main`, which shares the group. That commit is refused (`run concluded cancelled`); re-run its run (a re-run counts), or deploy the newer one (CR 12).
- **A rollback to a build that went live before the gate** may have no push run. `--skip-ci`, once.
